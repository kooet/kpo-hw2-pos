# ПОС — преподавательская оценка студентов

ДЗ №2 по КПО. Консольное приложение на C# (.NET 8): студенты, рубрикатор с критериями, оценки,
итог по весам и выгрузка ведомости в CSV. Внутри — DDD, архитектура Ports and Adapters
и три паттерна GoF. DI — `Microsoft.Extensions.DependencyInjection`, тесты — xUnit.

## Как запустить

Нужен .NET SDK 8.

```
dotnet build
dotnet test
dotnet run --project src/Pos.ConsoleApp
dotnet run --project src/Pos.ConsoleApp -- scenarios/demo.txt
dotnet run --project src/Pos.ConsoleApp -- --data data/pos.json
```

Первая команда `run` — обычный режим, всё вводится с клавиатуры. Вторая берёт ввод из файла
`scenarios/demo.txt`: там записан сквозной сценарий из задания. Третья сохраняет данные в JSON-файл,
и после перезапуска они никуда не пропадают. Без `--data` данные хранятся только в памяти.

Меню:

```
Студенты     1. Список   2. Добавить   3. Удалить
Рубрикатор   4. Список критериев   5. Добавить критерий   6. Изменить вес   7. Удалить критерий
Оценки       8. Выставить   9. Исправить   10. Отменить   11. Оценки студента
Итог         12. Итог студента   13. Ведомость итогов   14. Правило расчёта   15. Экспорт в CSV
```

Если ввести не число или номер не из списка, программа спросит ещё раз. Если нарушить правило
предметной области (балл 12 из 10, второй критерий «Контрольная»), программа покажет, что именно
нельзя, и продолжит работу.

### Сквозной сценарий

В `scenarios/demo.txt` по шагам сделано следующее:

1. Добавляются три студента; попытка добавить студента с пустым ФИО отклоняется.
2. Добавляются критерии «Домашние задания» (максимум 10, вес 0.4), «Контрольная» (100, 0.35)
   и «Активность на семинарах» (5, 0.25). Повтор «контрольная» и критерий с весом 0 отклоняются.
3. Выставляются оценки. Отклоняются балл 12 из 10 и вторая оценка по тому же критерию.
   Одна оценка исправляется (апелляция), другая отменяется.
4. Считается итог одного студента и ведомость по всем. Удалить критерий, по которому уже есть оценки,
   нельзя. Правило итога меняется на «только выставленные оценки, с округлением».
5. Ведомость выгружается в `demo-report.csv`.

Итоги в сценарии получаются такие: сначала 8.33, 4.74 и 3.19, после смены правила — 8, 6 и 9.

## Архитектура: Ports and Adapters

Решение разбито на отдельные проекты. Поэтому направление зависимостей проверяет компилятор:
домен просто не может сослаться на консоль или файлы, потому что у него нет такой ссылки.

```
Pos.ConsoleApp      →  Pos.Application, Pos.Infrastructure
Pos.Infrastructure  →  Pos.Application
Pos.Application     →  Pos.Domain
Pos.Domain          →  ни от чего не зависит
```

Все зависимости направлены внутрь, к домену.

- `Pos.Domain` — ядро. Студенты, рубрикатор, оценки, правила и расчёт итога. Здесь же порты
  хранения `IStudentRepository` и `IRubricRepository`: они описаны языком предметной области,
  а как именно хранить данные, домен не знает. Ни одной внешней зависимости.
- `Pos.Application` — сценарии (use cases): `StudentService`, `RubricService`, `EvaluationService`,
  `FinalGradeService`, `GradingRules`. Они достают агрегаты из репозитория, вызывают методы домена
  и сохраняют результат. Здесь же порт `IFinalReportExporter` для выгрузки ведомости.
- `Pos.Infrastructure` — исходящие адаптеры: `InMemoryStorage` и `JsonFileStorage` реализуют
  порты репозиториев, `CsvFinalReportExporter` — порт выгрузки. Здесь же маппинг DTO ↔ домен.
- `Pos.ConsoleApp` — входящий адаптер (`PosConsole`, консольное меню) и composition root
  (`CompositionRoot`), где DI-контейнер связывает порты с адаптерами.

Порт — это интерфейс, через который ядро общается с внешним миром. Адаптер — его конкретная реализация.
Например, чтобы хранить данные в базе, а не в JSON, достаточно написать ещё один адаптер для
`IStudentRepository` и `IRubricRepository` и поменять одну строку в `CompositionRoot`.
Домен и сценарии при этом не меняются.

## Карта DDD

### Единый язык

В коде используются те же слова, что в предметной области:

- студент — `Student`;
- критерий — `Criterion`, у него есть максимум (`MaxScore`) и вклад в итог (`Weight`);
- рубрикатор — `Rubric`, набор критериев курса;
- оценка — `Evaluation`: «этому студенту по этому критерию поставили такой балл (`Score`)»,
  с датой и необязательным комментарием;
- итог — `FinalGrade`, считается из оценок и рубрикатора.

Методы называются так же: `Student.Enroll`, `student.Grade`, `student.Correct`,
`student.CancelEvaluation`, `rubric.AddCriterion`.

### Entity и Value Object

Entity — объект, у которого есть идентичность: даже если его данные меняются, это всё тот же объект.
Например, если у критерия «Контрольная» поменять вес, это остаётся тот же критерий с тем же
`CriterionId`, и оценки по нему не теряются. Entity: `Student`, `Criterion`, `Rubric`.

Value Object — неизменяемое значение, которое сравнивается по содержимому. Два `PersonName("Иванова Анна")`
равны, а «изменить» значение можно только создав новое. Value Objects: `PersonName`, `CriterionName`,
`MaxScore`, `Weight`, `Score`, `FinalGrade`, `StudentId`, `CriterionId`.

Оценку `Evaluation` я тоже сделала value object. Оценка — это факт, а не объект со своей жизнью.
Исправить оценку значит заменить старый факт новым, а не редактировать старый.

Каждый value object сам проверяет себя при создании. Отрицательный балл, нулевой вес или пустое ФИО
просто не получится создать, поэтому дальше по коду эти проверки не нужны.

### Агрегаты

- `Rubric` — корень агрегата с критериями. Критерии меняются только через рубрикатор, поэтому он
  следит, чтобы названия не повторялись (без учёта регистра).
- `Student` — корень агрегата со своими оценками. Он следит, чтобы по одному критерию у студента
  была одна оценка: выставить второй раз нельзя, можно только исправить или отменить.

Оценки хранятся внутри студента, потому что меняются вместе с ним и правило «одна оценка на критерий»
касается именно студента. Рубрикатор — отдельный агрегат: он общий для всех студентов, и менять его
вместе с каждым студентом было бы неправильно.

### Инварианты и где они проверяются

- Балл не выходит за пределы критерия. `Score` не даёт отрицательных значений,
  `Criterion.EnsureAccepts` не даёт балл больше максимума.
- Оценку можно выставить только по критерию из рубрикатора. Конструктор `Evaluation` закрыт,
  создать оценку можно только через `EvaluationFactory`, а она сначала ищет критерий в рубрикаторе.
- Итог согласован с текущими оценками. Итог нигде не хранится, `FinalGradeCalculator` каждый раз
  считает его заново из оценок и рубрикатора. Если оценку отменить или исправить, итог сразу меняется.
- Одна оценка на критерий у студента — `Student.Grade`.
- Названия критериев не повторяются — `Rubric.Add`.
- Максимальный балл критерия после создания не меняется. Иначе уже выставленные оценки могли бы
  оказаться за пределами критерия.
- Критерий, по которому уже есть оценки, удалить нельзя — `RubricService.Remove`. Это правило
  затрагивает сразу два агрегата (рубрикатор и всех студентов), поэтому оно в сценарии, а не в `Rubric`.

### Repository

`IStudentRepository` и `IRubricRepository` — порты в домене. Реализации лежат в Infrastructure.
`JsonFileStorage` при загрузке восстанавливает объекты через обычные конструкторы и `EvaluationFactory`,
поэтому файл с баллом 12 из 10 не загрузится: домен это не пропустит, даже если данные пришли с диска.

### Domain Service

`FinalGradeCalculator` считает итог. Расчёт зависит сразу от студента (его оценки) и рубрикатора
(веса и максимумы), то есть от двух разных агрегатов. Поэтому это не метод `Student` и не метод `Rubric`,
а отдельный доменный сервис.

Итог считается по 10-балльной шкале: для каждого критерия берётся доля от максимума
(7 из 10 — это 0.7), доли усредняются с весами и умножаются на 10. Веса не обязаны давать в сумме
единицу: 0.4 / 0.6 и 2 / 3 дают одинаковый результат.

## Паттерны GoF

Я взяла по одному паттерну из каждой группы. Каждый закрывает конкретную проблему.

### Порождающий: Factory — `EvaluationFactory`

Проблема: чтобы создать корректную оценку, нужно знать рубрикатор (есть ли такой критерий, какой у него
максимум). Но студент про рубрикатор не знает, а рубрикатор не знает про студентов. Если бы оценки
создавались через `new Evaluation(...)` в разных местах, проверки пришлось бы повторять в каждом,
и где-нибудь их бы забыли.

Решение: конструктор `Evaluation` закрыт (`internal`), создать оценку можно только через фабрику.
Фабрика проверяет критерий и диапазон балла и нормализует комментарий. Ей пользуются и сценарии
выставления и исправления оценок, и загрузка из JSON — проверка одна для всех.

### Структурный: Decorator — `RoundedFinalGradeStrategy`

Проблема: итог иногда нужен точный (8.33), а для ведомости — округлённый до целого (8). Если делать
округление внутри каждого правила, получится дублирование и удвоение классов: «по всем критериям»,
«по всем критериям с округлением», «по выставленным», «по выставленным с округлением». Если округлять
в консоли, правило подсчёта размажется по интерфейсу, и CSV с экраном могут разойтись.

Решение: декоратор оборачивает любое правило итога и округляет его результат (0.5 — вверх). Он
реализует тот же интерфейс `IFinalGradeStrategy`, поэтому калькулятору всё равно, обёрнуто правило
или нет. Включается и выключается в меню, пункт 14.

### Поведенческий: Strategy — `IFinalGradeStrategy`

Проблема: правило итога может меняться. В конце курса нужен итог по всем критериям, где отсутствующая
работа — ноль. В середине курса преподавателю полезнее видеть средний балл только по уже выставленным
оценкам, иначе у всех будет «двойка» за ещё не написанный экзамен.

Решение: правило — отдельный объект. Сейчас их два: `WeightedAllCriteriaStrategy` и
`WeightedGradedOnlyStrategy`. `FinalGradeCalculator` получает правило параметром, а `GradingRules`
хранит выбранное. Новое правило (например, «блокирующий экзамен») — это новый класс и одна строка
регистрации в `CompositionRoot`. Калькулятор, сценарии и меню не меняются: меню само показывает
все правила из контейнера.

### Что я не стала делать

- Facade — сценариев немного, и они уже сгруппированы в четыре небольших сервиса. Ещё один
  класс-прослойка для консоли просто перенаправлял бы вызовы.
- Builder для рубрикатора — критерии добавляются по одному из меню, собирать рубрикатор целиком
  за один раз не нужно.
- Template Method для импорта — в задании нет импорта ведомостей, а экспорт сейчас в одном формате.
  Если появится второй формат (JSON, Excel), это хорошее место для Template Method.

## DI-контейнер

Всё связывается в `CompositionRoot.Build`. Там видно, какой адаптер стоит за каким портом: без `--data`
это `InMemoryStorage`, с `--data` — `JsonFileStorage`, а для выгрузки — `CsvFinalReportExporter`.
Один объект хранилища реализует оба порта репозиториев, поэтому студенты и рубрикатор лежат
в одном файле. Правила итога зарегистрированы как несколько реализаций `IFinalGradeStrategy`.
Контейнер собирается с `ValidateOnBuild`, поэтому забытая регистрация сразу даст ошибку при запуске.

Текущая дата берётся из стандартного `TimeProvider`, а не из `DateTime.Now`. Поэтому в тестах дату
можно подменить.

## Тесты

Тесты лежат в `tests/Pos.Tests`:

- `ValueObjectTests`, `RubricTests`, `StudentTests` — инварианты value objects и агрегатов;
- `EvaluationFactoryTests` — балл в пределах критерия, граница ровно на максимуме, критерий не из рубрикатора;
- `FinalGradeTests` — оба правила итога на числовом примере, декоратор округления (7.49 → 7, 7.5 → 8),
  итог меняется вслед за оценками, оценка по критерию не из рубрикатора;
- `UseCaseTests` — сценарии на хранилище в памяти: нельзя удалить критерий с оценками, смена правила
  меняет ведомость, экспорт отдаёт данные в порт (порт подменён фейком);
- `AdapterTests` — JSON сохраняет и загружает данные, испорченный файл не загружается, CSV открывается в Excel;
- `ConsoleTests` — сквозные сценарии через консоль и проверка, что DI выбирает нужное хранилище.

## Роль ИИ

ИИ использовался в качестве вспомогательного инструмента при разработке проекта. С его помощью удалось освежить знания C#, с которым я была знакома ранее, но некоторые аспекты языка и особенности его применения на практике подзабыла. Также ИИ помогал при обсуждении архитектурных решений, разборе отдельных частей реализации, поиске возможных улучшений и подготовке тестовых сценариев. Все предложенные решения проверялись на соответствие требованиям задания и корректность работы программы.
